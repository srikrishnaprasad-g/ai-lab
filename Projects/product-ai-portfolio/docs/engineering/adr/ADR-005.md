# ADR-005: Git & Branching Strategy

## Purpose

Define the standard Git workflow, branching strategy, commit conventions, and pull request requirements for all AI-Lab projects.

---

## Context

AI-Lab will contain multiple long-lived projects with continuous development.

A standardized Git workflow improves collaboration, reduces merge conflicts, simplifies releases, and provides a predictable development experience across projects.

---

## Decision

AI-Lab adopts a Git workflow centered around a stable production branch, an integration branch, and short-lived feature branches.

The branching model emphasizes simplicity while supporting future team collaboration.

---

## Standard Branches

### main

The `main` branch represents the production-ready state of the project.

Characteristics:

- Always deployable
- Protected from direct commits
- Source for production deployments

---

### develop

The `develop` branch serves as the primary integration branch.

Characteristics:

- Receives completed feature branches
- Used for integration testing
- May contain unreleased work

---

### feature/<feature-name>

Feature branches are created from `develop`.

Examples:

```
feature/user-authentication
feature/dashboard-redesign
feature/product-search
```

Characteristics:

- Short-lived
- Focused on a single feature
- Merged through Pull Requests

---

### release/<version>

Release branches are optional and intended for larger projects.

Examples:

```
release/v1.0.0
release/v2.3.0
```

Characteristics:

- Stabilization before production
- Bug fixes only
- Merged into both `main` and `develop`

---

### hotfix/<issue>

Hotfix branches are created directly from `main` for urgent production fixes.

Examples:

```
hotfix/login-timeout
hotfix/payment-error
```

Characteristics:

- High priority
- Production fixes only
- Merged into both `main` and `develop`

---

## Commit Convention

AI-Lab adopts conventional commit prefixes.

| Prefix | Purpose |
|---------|---------|
| feat | New feature |
| fix | Bug fix |
| docs | Documentation changes |
| refactor | Internal code improvements |
| style | Formatting and style changes |
| test | Tests |
| build | Build configuration |
| chore | Maintenance tasks |

Examples:

```
feat: add portfolio filtering

fix: resolve authentication timeout

docs: update technical foundation

refactor: simplify API client

test: add unit tests for dashboard
```

---

## Pull Request Requirements

Every Pull Request should:

- Pass all quality gates
- Successfully build
- Pass linting
- Pass TypeScript validation
- Include updated documentation when applicable
- Update relevant ADRs if architectural decisions change
- Receive reviewer approval before merge

---

## Branch Protection Rules

The `main` branch should be protected.

Recommended rules:

- No direct commits
- Pull Requests required
- Successful status checks required
- Reviewer approval required
- Linear history preferred

---

## Merge Strategy

Preferred merge strategy:

- Squash and Merge

Advantages:

- Cleaner history
- One commit per feature
- Easier rollback
- Improved readability

---

## Rationale

A lightweight Git workflow provides:

- Predictable development
- Clear release management
- Better collaboration
- Cleaner repository history

---

## Alternatives Considered

### GitHub Flow

Advantages:

- Very simple
- Fast delivery

Disadvantages:

- Limited separation between integration and production

---

### Git Flow

Advantages:

- Strong release management

Disadvantages:

- More complex
- Additional branching overhead

---

## Consequences

### Positive

- Consistent development workflow
- Cleaner Git history
- Easier code reviews
- Better release discipline

### Trade-offs

- Slightly more process than ad hoc branching
- Requires adherence to branch naming conventions
